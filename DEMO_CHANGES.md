# Demo Build — What Is Real and What Is Not

Branch: `feat/dummy`

This file is the honest inventory of the demo work on this branch. It exists so
that nobody — including us, three weeks from now — mistakes a scripted
demonstration for a working capability.

**The short version:** the geography and the camera network are real. The
vehicle identification is not. There is no ANPR (number-plate reading) model in
this project, and the Re-ID model cannot reliably tell similar vehicles apart.
Everything that appears to identify a specific vehicle is scripted.

## 3. Route identification

**Where:** the existing Vehicle Search page, in a card titled "Narrow the
search" — a number-plate field and a last-seen-camera dropdown, both optional.
Results render on the existing Vehicle Search results page.

There is no separate page and no extra tab. Leaving both fields blank runs the
original photo-only search against the real backend, entirely unchanged.

### What is genuinely real

- **The 10 camera locations.** Real rows from this project's own `camera`
  table (Ahmedabad cluster), with their real coordinates.
- **Every distance.** Real haversine great-circle distance between real
  coordinates. The hops in a demo route are typically 1.2–5.3 km, because
  that is how far apart those cameras actually are.
- **The corridor-walk algorithm.** This is the real proposed strategy, not a
  stored path: from the last-seen camera, find the nearest not-yet-visited
  camera within a 4 km radius, hop to it, repeat. Nothing is hardcoded — change
  the starting camera and the route genuinely recomputes.
- **The radius rule and its failure mode.** `SEARCH_RADIUS_KM = 4`. When no
  camera is in range the search widens through `[4, 6, 8]` km rather than
  stopping, and each widened hop is labelled as crossing a coverage gap and
  takes a confidence penalty.
- **Travel times.** Derived from the real distance at ~28 km/h average urban
  speed, so timings are consistent with the geography.

### What is scripted

- **The plate match.** There is no ANPR model. A plate is treated as "read"
  if the normalised input is at least 8 characters; that is a length check,
  not recognition.
- **Which cameras the vehicle was "seen" at.** The walk assumes a hit at
  every camera it steps to. No sighting data is consulted.
- **All confidence values.** Generated by formula: plate matches decay from
  0.97 by 0.015 per hop, image-only matches from 0.91 by 0.045 per hop.
  A further 0.06 is deducted for any hop that crossed a coverage gap. The
  steeper image decay is deliberate — it is the argument for asking which
  camera the vehicle was last seen at — but the numbers are invented.
- **The northward constraint.** The walk only steps to cameras further north,
  standing in for direction-of-travel inference the real system would do from
  consecutive sightings. Without it the route doubled back on itself.
- **Vehicle class.** Always reported as `car`.

### The staged processing

The user asked that results not appear instantly, so the pipeline is shown
working before the route draws. Stages run **on the search page**, then it
redirects to the results map.

| Stage | Shown for |
|---|---|
| Reading number plate | 1.6 s |
| Matching against vehicle registry *(or: plate unreadable — falling back)* | 1.4 s / 1.5 s |
| Locating plate at the reported camera *(or: building visual fingerprint)* | 1.5 s |
| Expanding search to cameras within 4 km | 2.0 s |
| Reconstructing route | 1.5 s |

Totals: **8.0 s** with a readable plate, **8.1 s** on the image-fallback path,
**5.0 s** with a camera but no plate. These delays are cosmetic — they pace the
UI, they are not measured work.

### Demo paths worth showing

1. **Plate `GJ01AB1234` + any camera** → full route, plus a watchlist alert.
2. **Blank plate, camera only** → the image-fallback path, with confidence
   visibly degrading across hops.

Starting from Navrangpura Cross Roads gives a 6-camera route over 41 minutes.

## 4. Watchlist alerts (24/7 feed)

**Where:** a bell icon in the header, beside the "Synced" indicator.

This models the intended behaviour: the ingest service pulls frames from every
camera around the clock, matches each detected vehicle against the police
wanted list, and raises an alert on a hit — with nobody having searched.

### Behaviour

- An alert arrives **every 60 s**; the first lands **8 s** after load, so a demo
  never opens to an empty panel.
- Each alert fires three things at once: a **corner toast** (visible 9 s), the
  **alert sound**, and a **badge increment** on the bell.
- Clicking the bell opens the persistent panel — all alerts this session,
  newest first, unread ones highlighted. Opening marks all read.
- Panel footer shows the session count and "Clear all". A mute toggle sits in
  the panel header.
- The feed is capped at 40 alerts so a long-running demo cannot grow unbounded.

### What is scripted

**Everything.** Nothing is read from the ingest pipeline or the database.

- **7 wanted vehicles** rotate in order: `GJ01AB1234`, `GJ05CD5678`,
  `GJ18EF9012`, `GJ27GH3456`, `GJ06JK7890`, `GJ03LM2244`, `GJ12NP8833`,
  across three severities (Critical / High / Medium).
- **Case references** (`FIR 0412/2026`, `EXC 1189/2026`, `NBW 0233/2026`, …)
  and issuing authorities are invented.
- **Plate confidence** is `0.88 + random()*0.11`.
- **Timestamps** are the moment the alert is generated.

The only real ingredient is the **camera each alert names**, drawn at random
from the 10 real cameras.

Verified: six consecutive alerts produced six distinct plates across four
different cameras, so it does not read as a loop.

### The sound

Synthesised in-browser with the Web Audio API — a two-tone rising chime,
repeated twice, ~0.8 s. Deliberately not an audio file: nothing to 404
mid-demo, no new dependency.

**Browsers block audio until the user interacts with the page.** If the first
alert arrives before you have clicked anything, the toast appears silently.
Click once after loading and every later alert has sound. Gain is ~0.14; for a
room with a projector, raise the values in `alertSound.ts`.

## 6. A real bug found along the way

Feeding a route with `detection_confidence: null` through the results header
rendered the literal string **`detection undefined`**. The pre-existing code
only guarded that field behind the `used_whole_image_fallback` flag, so any
other null slipped through.

Fixed. The real search path is unaffected.

Two demo-breaking presentation bugs were also caught by screenshotting rather
than assuming: map tiles were showing **"API KEY REQUIRED"** watermarks (the
CartoDB URL now needs a key — switched to the keyless OpenStreetMap tiles the
GIS page already uses), and the map sat at a fixed zoom with **4 of 6 markers
off-screen** (added auto-fit to the route bounds).

## 7. Labels

Per instruction, no "FUTURE SCOPE" or "simulated" badges appear anywhere in the
UI. The honest accounting lives in code comments — the file header of
`demoInvestigation.ts` and `AlertFeedContext.tsx` — where maintainers will find
it and audiences will not.

**This shifts a burden onto whoever presents.** The UI no longer says the
vehicle matching is scripted, so the presenter has to. Claiming working ANPR
unravels badly under a direct question; "here is the algorithm running on our
real camera network, ANPR is the next build" is both true and stronger.

## 9. To make this real

- **Route identification** needs an ANPR model. The corridor walk, the radius
  rule, the gap handling and the UI all stay; the scripted plate match is
  replaced by real reads, and each hop is confirmed against actual sightings
  rather than assumed.
- **The alert feed** needs the ingest service to push watchlist hits. Swap the
  timer in `AlertFeedContext` for a subscription; the alert shape and the whole
  UI stay as they are.
- **Vehicle Re-ID**, measured earlier in this project, rates a motorcycle
  against a car at 0.8068 similarity and produced a 36% false-match rate at a
  0.80 threshold. Raising the threshold to 0.90 and filtering impossible routes
  removed the provably-wrong matches but did not make identification
  trustworthy. This is the honest blocker behind the route feature.
