# Database Architecture

**Database:** PostgreSQL 16 with the PostGIS extension, running locally as `sentinel_model1_db`.

**ORM:** Prisma, pinned to `6.19.3` (both `prisma` and `@prisma/client`) — not the latest major. Prisma 7+ hard-rejects the `url = env("DATABASE_URL")` datasource syntax that the project's reference schema uses, forcing a `prisma.config.ts` + adapter pattern instead. Prisma 6.x is the newest line that keeps the classic, simpler `PrismaClient` construction this project's `PrismaService` relies on.

**Connection pattern:** a single global `PrismaModule` (`@Global()`) exports one `PrismaService`, injected into every module that needs database access. No module creates its own database connection.

## Introspection Workflow

The database schema is **not** authored inside this backend project. It was created once via `../../../model1_fresh_setup.sql` at the repo root, and `prisma/schema.prisma` here is generated by introspecting that live database (`npx prisma db pull`), then reconciled to match the hand-maintained, fully-annotated reference copy at `../../../schema.prisma` (repo root) — which uses camelCase model names and explicit `@map()` directives instead of the raw snake_case introspection output.

**From this point forward, schema changes go through `npx prisma migrate dev` only.** The SQL setup script is a one-time historical step and must not be re-run or hand-edited once real data exists.

## Tables

| Table | Purpose |
|---|---|
| `department` | The government departments that own cameras (Police, RTO, etc.) |
| `app_user` | Login accounts and their roles |
| `refresh_token` | Hashed refresh tokens, enabling revocable sessions |
| `camera` | The core camera registry — location, ownership, technical details, integration score |
| `vendor_lookup` | Curated brand/model → ONVIF-support lookup table (the scoring "fast path") |
| `scoring_verification` | AI-guessed ONVIF answers awaiting human confirmation |
| `camera_status_history` | Time-series log of camera reachability checks |
| `audit_log` | Every create/update/delete/export action, for accountability |

Full column-level detail lives in the schema file itself (`prisma/schema.prisma`) and in `../../../Model1-PRD.md` Section 6/6a — not duplicated here.

## Known Introspection Caveat

Postgres `CHECK (... IN (...))` constraints (e.g. `role`, `camera_type`, `onvif_status`) introspect as plain `String` fields in Prisma, not native enums, because they're implemented as `CHECK` constraints rather than Postgres `ENUM` types. This is expected and intentional — do not attempt to convert them without a deliberate migration decision. Value constraints are enforced at the application layer via `class-validator`'s `@IsIn([...])`.
